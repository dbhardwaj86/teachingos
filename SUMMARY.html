The big picture

SAMAGRA is the control room for a one-person physics teaching business.

It does not replace the tools that already work.

It watches them, lines up the work, and makes sure nothing reaches a student without a human "yes".

Local-first Built for one person Read-only + owner capture Quality over speed

01 · The one idea

SAMAGRA owns one thing: the journey of each piece of work.

From a rough idea to something published.

Every tool keeps owning its own content. SAMAGRA just tracks where each item is on its journey, and points at where it lives.

02 · The lifecycle

Every item walks the same four steps.

1
Capture

An idea comes in — often a quick note from the phone.

2
Enrich

An agent drafts it into real teaching material.

3
Review

Another agent checks it. Code and physics are checked separately.

4
Publish

Deepak approves. Always. This step is never automated.

03 · The company

SAMAGRA is run like a small company. The titles are just plain roles.

The "company" is just a way to talk about it. It is not extra software — no special tables, no extra machinery.

04 · Rules we never break

Four lines hold the whole thing together.

Read-only by default

SAMAGRA can write in exactly one place — and only after a human "yes". Everywhere else, it only reads.

One sacred gate

Nothing publishes without Deepak. That approval is never handed to a machine.

Freeze the shape

Big ambitions can be named today. They are not allowed to add anything to build today.

A built-in off-switch

If SAMAGRA isn't clearly saving time, we stop and go back to the old tools. The exit is written down on purpose.

The factory learned Deepak's style
New (25 Jun): the factory now knows the owner's voice. The biggest question in any AI-writing tool is "does it sound like me?" This step answers it by reading all 59 of Deepak's written chapters and distilling them into a compact, versioned style profile — five facets: how he uses words, how he sequences ideas, how he reaches for analogies, how precise/corrective he is (drawn from the actual "clarified/corrected/noted" tags in his chapters), and what he picks to cover. The profile is saved as a small file right in the project, so it travels with the code and any future AI writer can read it before drafting. There is also a gentle style-fit score — a number that says how on-voice a draft is — but it is purely advisory: it shows up as information, never as a decision. Nothing decides for the owner; the publish gate is unchanged. Completely read-only and deterministic — no AI call, no internet, no new write paths. Built test-first across ten tasks; a final review confirmed all four safety rules held. 385 automated tests, 384 passing (the one red is a pre-existing environment stub unrelated to the factory — it fails on main too). Merged into the main copy and backed up to GitHub.

…and now the style profile can learn
New (25 Jun): a learning loop for the owner's style. The style profile from the step above isn't frozen — this step lets it improve from Deepak's own feedback, but only when he says so. When the owner marks a draft as needing "changes", the factory can read those edits and suggest small tweaks to the style profile (e.g. "lean a little more corrective here"). It's all read-only and offline — no AI call, no internet, no secrets; the suggestions and approvals are just recorded in the project's own bookkeeping. New (25 Jun): the factory's first AI-writing step — "Samadhan". Until now every piece the factory made was built by fixed rules. This is the first lane that actually writes new prose with AI: hand it a textbook chapter and it produces a short misconception brief — a piece in Deepak's voice that names a common student mistake and clears it up. Second, the lane is opt-in: a plain textbook chapter won't trigger AI writing unless you explicitly ask for it. The AI key lives in a private local file that's never shared or committed, and the AI only ever writes its draft to this machine — it never reaches out and changes any of the source tools. A course-correction we just made (21 Jun)

We've been building the control room (the screens) ahead of the one write — turning a phone note into a draft, the part that actually saves Deepak time. A coherence check this session asked the honest question: is a full "OS-style" desktop the right thing to build first, or is it quietly growing bigger than a one-person back-office tool needs? Two independent reviews said the build is solid but the direction had drifted from the original plan, which had deliberately dropped the word "OS". Deepak's call (now decided): keep the control room a plain operator console — a way to see and run the work, never a product; no new toys (no games beyond the one we have, no app store, no outside apps); and before we build a phone version, we measure it — does the control room actually save time on a few real tasks versus the old way? If not, we stop dressing it up and get back to the one write. The one write stays the real prize.

06 · Decided & parked

What's settled, and what's named-but-not-built.

Decided

  • The headline number is time savedMinutes of Deepak's attention per published item.
  • Reuse the existing topic list~100 tags we already have — never a sprawling map.
  • First self-driving lane is refreshing read-only dataThe safest possible thing to automate — and only later.
  • Published work may go publicThrough a separate front — never SAMAGRA itself.
  • The control room stays a plain consoleA way to see and run the work — never a product; no extra apps or games.
  • Measure before building moreA phone version waits until the screens prove they save real time.

Parked (named, not built)

  • A coverage scoreboardWhich topics are well-covered, which have holes.
  • Learning from past approvalsSo drafts start closer to Deepak's taste.
  • Self-driving lanesEarned slowly, one safe lane at a time.
  • A "keep going while I'm away" valveFor exam-season crunch, tightly limited.
